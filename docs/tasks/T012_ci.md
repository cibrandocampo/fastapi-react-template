# T012 — Continuous integration

**Plan**: docs/plans/template-base.md · **Depends on**: T011

## Objective
Every PR and push to main runs lint, unit tests with coverage, E2E and the image build; images are
pushed to Docker Hub only when the repository has the credentials.

## Step 1 — `ci.yml`
Jobs (all through Docker, as locally):
- `backend`: build the dev backend, ruff check/format, pytest with coverage against the dev db and
  Mailpit (the compose already sets `MAILPIT_API_URL` / `MAILPIT_SMTP_HOST` for the email integration test).
- `frontend`: npm ci, lint, format check, vitest coverage.
- `e2e` (needs both): `make e2e`, upload the Playwright report on failure.
- `audit` (non-blocking): pip-audit, `npm audit --omit=dev --audit-level=high`.
- `image` (needs e2e): buildx multi-arch (amd64, arm64) with `APP_VERSION` from `git describe`; push
  only when `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` secrets exist and the event is a push to main
  (`latest`) or a published release (`<version>`, `stable`); otherwise build only (amd64, no push).
  Image name from the `DOCKER_IMAGE` repository variable.
`permissions: contents: read`; concurrency cancels superseded PR runs only.

## Step 2 — Other workflows
`weekly-rebuild.yml` (Mondays, no cache, same push condition), keep `sync-disposable-email-domains.yml`,
`.github/dependabot.yml` (pip, npm, docker, github-actions; weekly).

## DoD
1. Workflows parse; `actionlint` (in its Docker image) clean.
2. CI green on the PR, with the image job building without pushing (no secrets in this repo).

## Implementation notes
- `ci.yml`: jobs backend, frontend, audit (advisory), e2e (`make e2e`, report kept on failure), image
  (multi-arch push of `latest` / version + `stable` only with `DOCKERHUB_*` secrets and `DOCKER_IMAGE`,
  otherwise amd64 build without push). Everything through Docker, as locally.
- `weekly-rebuild.yml` rebuilds `latest` (main) and `stable` (latest release) without cache, skipping
  without credentials or releases; `sync-disposable-email-domains.yml` kept (checkout bumped);
  `dependabot.yml` for pip, npm (frontend, e2e), docker, compose and actions.
- First CI run on the PR failed in Backend: the production `.dockerignore` (T010) excluded
  `backend/requirements-dev.txt`, which the dev backend image needs (same build context); locally a
  cached image hid it. Fixed in 38b9281 and checked with a `--no-cache` build of both dev images.
- Evidence: `actionlint.txt` (clean), `ci.txt` (all jobs pass on PR #1; the image job built without
  pushing — no secrets in this repository).

### Blockers
- **B1**: `.github/workflows/ci.yml:157-163` (metadata-action `Tags` step). Expected: `latest`
  only from a push to main, as the plan says. Found: no `flavor:` input, so metadata-action's default
  `latest=auto` adds `latest` whenever `type=semver` produces a tag. Every published release
  therefore also pushes `latest`, pointing it at the release tag rather than main (for a hotfix
  tagged off an older commit, `latest` goes back in time until the next weekly rebuild). Evidence:
  `metadata-action-latest.txt` (upstream README: "`latest` ... will be generated by default (`auto`
  mode) for ... type=semver"). Fix: add `flavor: latest=false` to that step; the explicit
  `type=raw,value=latest,enable=...` line still covers main.

### Observations (non-blocking)
- **O1**: `ci.yml:162` `stable` is enabled for any `release: published`, pre-releases included,
  while `weekly-rebuild.yml` rebuilds `stable` from `gh release view` (latest non-prerelease).
  Consider `enable=${{ github.event_name == 'release' && !github.event.release.prerelease }}`.
- **O2**: concurrency for main/release does not cancel running runs, but GitHub still replaces a
  pending run in the same group with a newer one; harmless (the newer commit includes the older),
  the comment "main and releases always finish" is slightly too strong.
- **O3**: `weekly-rebuild.yml` `gh release view ... 2>/dev/null || true` turns an API error into a
  silent "No release yet" skip of `stable`; distinguishing "no release" from a failure would avoid
  missing a security rebuild unnoticed.
- **O4**: arm64 is built only when pushing (main/release); a change that breaks the arm64 build is
  first seen after merge. Acceptable trade-off for PR speed, worth a line in the CI skill.
- **O5**: `sync-disposable-email-domains.yml` uses `peter-evans/create-pull-request@v7` (v8.1.3 is
  current); Dependabot (github-actions) will propose it. Actions are pinned by major tag, not SHA.

### Round 2 (QA round 1: B1)
- B1: the Tags step sets `flavor: latest=false`; `latest` comes only from the explicit main rule.
- O1: `stable` only for releases that are not pre-releases (matches the weekly rebuild's "latest
  release"). O2: the concurrency comment says what GitHub really does. O3: the weekly rebuild skips
  `stable` only on "release not found"; any other API error fails the job. O5:
  `peter-evans/create-pull-request@v8`. O4 (arm64 only built on main/releases) kept: emulated arm64 on
  every PR is slow; a broken arm64 build shows on the main run, before any release.
